# 第 4 课：输出校验与小型评测

> 本课约 30 分钟。上一课证明“函数正常返回”不等于“业务判断正确”。本课再证明“JSON 能解析”也不等于“可交给业务”。

## 1. 三道不同的关

把模型返回值看成来自外部服务的原始文本，依次检查：

1. **语法关：** `json.loads` 能否把文本解析成 JSON 值？例如 `not-json` 会失败。
2. **合同关：** 根节点是否是对象，是否有必需字段，字段类型和值域是否合法？例如 `[]` 语法正确，却不是分类对象；`{"intent":"banana"}` 有字段，却不是允许的意图。
3. **业务关：** 对照有标签样本，这次分类是否符合客户真实意图？例如 `do not refund` 被判 `refund`，前两关即便通过，第三关仍失败。

三关对应不同处理：语法和合同失败应拒绝返回业务结果，必要时在有限重试预算内重试或转人工；业务质量要靠标注样本和持续评测改进。把解析异常直接吞掉并填成 `other`，会把技术故障伪装成真实分类。

## 2. 先在纸上判，再写解析器

本章练习函数 `parse_model_object(text, required)` 的范围是**语法关 + 合同关的一部分**：接受纯 JSON 或完整的 `json` 代码围栏；只要求根节点为对象且包含 `required` 中的键。它不会判断意图枚举、数值范围或分类正确率。

| 原始文本 | `required` | 本练习应如何处理 | 原因 |
|---|---|---|---|
| `{"intent":"refund"}` | `{"intent"}` | 接受 | 对象且字段存在 |
| 完整的 `` ```json ... ``` `` 围栏 | `{"intent"}` | 接受围栏中的 JSON | 有些模型会包代码围栏 |
| `not-json` | 空集合 | 拒绝 | 无法解析 JSON |
| `[1,2]` | 空集合 | 拒绝 | 根节点不是对象 |
| `{"answer":"ok"}` | `{"intent"}` | 拒绝并指出 `intent` | 缺少必填字段 |

注意 `json.loads('null')` 会得到 `None`，`json.loads('42')` 会得到整数，所以不能只写“能解析就返回”。围栏也必须是完整包裹：不要从任意文字中猜测 JSON 起止位置，更不要替模型补逗号和引号。

## 4. 解析之后还差哪一步

`parse_model_object` 只保证拿到了含必填字段的字典。如果下一层要消费分类结果，至少还要检查枚举值：

```python
payload = parse_model_object(raw_text, {"intent"})
intent = payload["intent"]
# JSON 字符串、数字、空值都可能出现在同一个字段位置；业务只接受两个标签。
if intent not in ("refund", "other"):
    raise ValueError("unsupported intent")
```

若还要使用 `confidence`，需检查字段存在、类型是合适的数值、值在 `0..1`，并单独做概率校准；`bool` 在 Python 中是 `int` 的子类，简单的 `isinstance(value, (int, float))` 还会意外接受布尔值。这些检查不属于本次解析练习，但你应知道它们在什么位置补。即使全部通过，仍只得到**分类建议**，不是退款授权。

## 6. 课末小测

先独立回答，再展开下方提示：

1. `confidence=0.92` 能否当成“92% 正确”并自动退款？
2. `{"intent":"banana"}` 是合法 JSON 对象，为何仍不能交给业务？
3. `Please do not refund order SO-1` 为何被离线替身误判？
4. 一个模型正确判断为 `refund` 后，应用能否直接调用退款支付接口？

<details>
<summary>核对要点</summary>

1. 不能。`0.92` 是硬编码演示值；真实模型的自报数字也需要校准验证。
2. 业务合同只允许已定义意图。当前示例尚未检查枚举，这正是发现的缺口。
3. 替身只检查是否包含 `refund`，没有处理否定语义。
4. 不能。分类只是建议；订单事实、金额、权限和审批都由业务系统核验。
